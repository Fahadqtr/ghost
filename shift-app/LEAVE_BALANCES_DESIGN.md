# المرحلة ٢ — نظام أرصدة الإجازات (Leave Balances) — تصميم للمراجعة فقط

> **حالة:** تخطيط فقط. لا SQL مُطبّق، ولا تعديل على الإنتاج، ولا دمج، ولا نشر.
> الفرع: `claude/leave-balances-v2` — المشروع: shift-scheduler (`fibkwudabuwfjqpyeeng`).

---

## 0) ملخّص القرار الجوهري (مصدر الحقيقة الوحيد)

**المستحق والمرحّل والتعديلات الإدارية تُخزَّن؛ أما «المستخدَم» و«المتبقّي» فيُحسبان اشتقاقاً من الإجازات المعتمدة — ولا يُخزَّنان أبداً.**

السبب: «المستخدَم» يتغيّر مع كل عملية (إضافة/تعديل تاريخ/إلغاء اعتماد/حذف). لو خزّنّاه، لوجب تحديثه بدقّة في كل مسار — وأي مسار منسيّ = اختلاف أرقام دائم. باشتقاقه من جدول `leaves` (مصدر الحقيقة الوحيد لما استُهلك فعلاً) يستحيل أن تختلف الأرقام. في المقابل، البيانات المُخزَّنة (السياسة، المرحّل، التعديلات) نادرة التغيّر وكلّها **صريحة وموثّقة وقابلة للتدقيق**.

الصيغة:
```
المتبقّي = المستحق + المرحّل + Σ(التعديلات الإدارية) − المستخدَم
المستخدَم = Σ أيام الإجازات المعتمدة داخل حدود السنة (اشتقاق لحظي)
```
للأنواع «بلا حدّ» (unlimited): المتبقّي = ∞ (يُعرَض «—»)، والمستخدَم يُحسب للعرض فقط.

## 2) سياسات RLS المقترحة (تطابق النمط القائم)

**`leave_policies`**
- SELECT `read_leave_policies`: `is_owner() OR team = coalesce(jwt.app_metadata.team,'w1')`
- ALL `write_leave_policies`: `is_owner() OR (jwt.role='admin' AND team = jwt.team)` (USING + CHECK)

**`leave_ledger`**
- SELECT `read_leave_ledger`: `is_owner() OR team = jwt.team OR emp_id = (self via emp_no)`
  - `self`: `emp_id IN (select id from employees where emp_no = jwt.user_metadata.emp_no)` — يتيح للموظف رؤية قيوده فقط.
- INSERT `write_leave_ledger`: `is_owner() OR (jwt.role='admin' AND team = jwt.team)` (CHECK)
- **لا UPDATE ولا DELETE** لأحد (immutable)؛ التصحيح بقيد معاكس. (اختيارياً: DELETE للمالك فقط للطوارئ.)

**`archived_leave_ledger`**: SELECT للـ`admin`/owner (يماثل `archived_leaves`).

جميعها: `revoke all ... from anon, authenticated; grant select (+ insert للمصرّح) to authenticated` — بنفس أسلوب Phase 1، والموظف لا يملك أي مسار كتابة على الرصيد.

## 3) الدوال والمشغّلات اللازمة

### أ) `fn_leave_used(p_emp uuid, p_year int, p_type text) returns numeric`
```
مجموع، لكل إجازة معتمدة (status='معتمد') من هذا النوع لهذا الموظف:
  overlap = (least(to_date, YYYY-12-31) - greatest(from_date, YYYY-01-01) + 1)
  إن كانت overlap > 0 تُضاف (وإلا صفر)
```
يعالج **الإجازة الممتدة بين سنتين** تلقائياً (قصّ المدة على حدود السنة). `stable`، يحترم RLS (يعمل ضمن صلاحية المستدعي).

### ب) `fn_leave_balance(p_emp uuid, p_year int)` → صفوف لكل نوع
يعيد: `type, entitled_days, unlimited, carryover, adjustments, used, remaining` بضمّ `leave_policies` + تجميع `leave_ledger` (carryover/initial/adjustment/override) + `fn_leave_used`. `remaining = unlimited ? null : entitled + carryover + adjustments − used`.

### ج) `my_leave_balances(p_year int)` — RPC للموظف (SECURITY DEFINER)
يحلّ موظف المستدعي من `emp_no` (jwt.user_metadata) + الوردية، ويعيد **رصيده هو فقط**. يمنع تسريب أرصدة الآخرين حتى لو كانت سياسة القراءة على مستوى الوردية.

### د) امتداد `audit_capture()` (CREATE OR REPLACE — مع الحفاظ على كل الفروع الحالية)
فرعان جديدان:
- `leave_policies`: ملخّص «ضبط سياسة رصيد (النوع سنة) → مستحق/بلا حدّ»، و`changed` يتتبّع `entitled_days`/`unlimited`/`max_carryover` قديم→جديد.
- `leave_ledger`: عند INSERT ملخّص «أضاف {مرحّل/تعديل/تجاوز} رصيد (±N النوع سنة) لـ <اسم الموظف>: <السبب>». **السبب يظهر** لأنه مبرِّر التعديل ومقصود للتدقيق.

### هـ) مشغّلات تدقيق
`create trigger trg_audit after insert or update or delete on public.leave_policies ... execute audit_capture();` ومثلها على `leave_ledger`. (يحقّق: كل تعديل إداري يظهر في Audit Log الحالي.)

### و) امتداد `shift_archive_user()` (CREATE OR REPLACE — يبقى معامليّاً)
قبل حذف الموظف: نسخ صفوف `leave_ledger` الخاصة به إلى `archived_leave_ledger`. (إجازاته المعتمدة تُنقل أصلاً إلى `archived_leaves` فيصبح «المستخدَم» المشتق = 0 بعد الحذف، بلا قيود يتيمة.) **يجب اختباره داخل BEGIN/ROLLBACK كما في Phase 1 والتأكد أنه لا يستدعي خدمة خارجية.**

### ز) (اختياري) `fn_rollover_year(p_team, p_from_year)` — ترحيل الرصيد
يحسب المتبقّي لكل موظف/نوع، ويُنشئ قيد `carryover` في `p_from_year+1` مقصوصاً بـ`max_carryover`. يُشغّله المالك/المسؤول يدوياً (لا تلقائي) لتفادي الترحيل المزدوج، وكل قيد موثّق.

## 5) خطة Migration للبيانات الحالية (كلها إضافية، غير هدّامة)

1. `lb_tables`: إنشاء `leave_policies` + `leave_ledger` + `archived_leave_ledger` + فهارس + تفعيل RLS + السياسات + REVOKE/GRANT.
   - فهارس مقترحة: `leave_ledger(team, emp_id, year, type)`، `leave_policies(team, year)`، وفهرس على `leaves(team, emp_id, status, from_date)` لتسريع الاشتقاق.
2. `lb_functions`: `fn_leave_used`, `fn_leave_balance`, `my_leave_balances`.
3. `lb_audit`: `CREATE OR REPLACE audit_capture` (بفرعَي الجدولين) + مشغّلا `trg_audit`.
4. `lb_archive`: `CREATE OR REPLACE shift_archive_user` (مع أرشفة الـledger).
5. **بذر السياسات**: إنشاء صفوف `leave_policies` لسنة 2026 لكل وردية بقيم مبدئية (يضبطها المالك لاحقاً). **لا حاجة لبذر «المستخدَم»** (مشتق). لا ترحيل للسنة الأولى (أو يُضبط صراحة).
6. لا تعديل ولا حذف على `leaves` القائمة؛ الإجازات المعتمدة الحالية تُحتسب مستخدَماً تلقائياً.

كل خطوة تُطبَّق وتُختبر منفردة داخل `BEGIN/ROLLBACK` على الإنتاج (كما في Phase 1)، مع توقّف فوري عند أي فشل، وامتداد `shift_archive_user` يُفحَص أولاً للتأكد من معامليّته.

## 6) خطة الاختبار المفصّلة

### قاعدة البيانات (BEGIN/ROLLBACK، بيانات اختبار فريدة، لا أثر دائم)
- **الاشتقاق**: مستحق/مرحّل/تعديل/مستخدَم/متبقّي لكل نوع؛ تحقّق يدوي من القيم.
- **الامتداد بين سنتين**: إجازة 2026-12-28→2027-01-03 → تُقسَّم صحيحاً بين سنتَي 2026 و2027.
- **إلغاء الاعتماد**: اعتماد ثم إلغاء → المستخدَم يعود فوراً (لأنّه مشتق) + Audit يسجّل تغيّر الحالة.
- **تعديل تاريخ إجازة معتمدة**: المستخدَم يُعاد حسابه تلقائياً.
- **حذف موظف**: أرشفة الموظف + إجازاته + قيود الـledger؛ لا قيود يتيمة؛ لا مستخدم auth متبقٍّ (يماثل فحص Phase 1).
- **RLS**: owner يرى كل الورديات؛ admin وردية واحدة فقط؛ viewer عبر `my_leave_balances` يرى نفسه فقط ولا يرى غيره؛ لا كتابة للموظف؛ الكتابة المباشرة على الجداول مرفوضة للموظف.
- **التدقيق**: قيد سياسة وقيد ledger يظهران في `audit_log` بالملخّص العربي والسبب.
- **سلامة الفشل**: فشل التدقيق لا يُعطّل العملية الأصلية.
- **التجاوز**: إدراج قيد `override` بسبب إلزامي يظهر في الرصيد والتدقيق.

### الواجهة (تشغيل محلي للفرع مقابل باكند الإنتاج، عبر Relay كما في Phase 1)
- بطاقة الرصيد للموظف (viewer): مستحق/مستخدَم/متبقّي صحيحة، ولا يرى غيره.
- شاشة الأرصدة الإدارية (admin/owner): كل الموظفين، فلتر السنة والنوع.
- تنبيه قبل الإرسال عند تجاوز الرصيد (موظف)، وتجاوز المشرف بسبب مكتوب.
- لوحة تعديل الرصيد: رفض الحفظ دون سبب.
- Offline/Outbox: إضافة تعديل رصيد دون إنترنت ثم مزامنته.
- RTL/جوال، ولا كسر لأي شاشة قائمة.

### الانحدار (Regression)
- مسار الإجازة الحالي (إضافة/تعديل/حذف/تقديم موظف) دون تغيّر.
- `pull()` الموسّع لا يكسر التحميل.
- Audit Log وأرشفة الموظفين وملفات Word وبقية الشاشات تعمل.

## 7) المخاطر والحالات الحدّية

| # | الخطر / الحالة | المعالجة |
|---|---|---|
| 1 | طريقة عدّ الأيام (تقويمية مقابل أيام عمل/استثناء العطل) | افتراضياً أيام تقويمية داخل السنة (يطابق `inclusiveDays`) + خيار `count_holidays`. **قرار للمالك.** |
| 2 | «غياب»/«عارض» بلا حدّ أم بحدّ؟ | يُضبط عبر `unlimited` لكل نوع في السياسة. **قرار للمالك.** |
| 3 | موظف جديد منتصف السنة | قيد `initial` صريح يحدّد رصيده الابتدائي (موثّق) بدل احتساب آلي مبهم؛ (اختياري: تناسب آلي لاحقاً). ملاحظة: `cycle_start` الحالي هو مرساة الجدول لا تاريخ التعيين. |
| 4 | تجاوز الرصيد | الموظف: تنبيه فقط (لا يُحسب المعلّق). المشرف: يعتمد مع قيد `override` وسبب إلزامي. لا حجب صلب على مستوى القاعدة لأن المعلّق لا يُحتسب. |
| 5 | استمرار «المستخدَم» صحيحاً بعد أي تعديل | مضمون بالاشتقاق من `leaves` (لا عدّاد مخزَّن). |
| 6 | تسريب أرصدة عبر RLS | الموظف عبر `my_leave_balances` فقط؛ سياسة القراءة على الوردية للمسؤول/المالك. |
| 7 | ضجيج التدقيق | فرع مخصّص في `audit_capture` بملخّصات مفيدة؛ الـledger إضافة-فقط فيقلّ التحديث. |
| 8 | أداء الاشتقاق | فهرس `leaves(team, emp_id, status, from_date)`؛ الحساب لكل موظف/سنة خفيف. |
| 9 | حدود المناطق الزمنية للتواريخ | كل التواريخ `date` (بلا وقت) فلا أثر للمنطقة الزمنية على العدّ. |
| 10 | ترحيل مزدوج | `fn_rollover_year` يدوي + قيد `carryover` واحد لكل (موظف/سنة/نوع) يمكن التحقّق منه قبل الإنشاء. |
| 11 | تعديل `audit_capture`/`shift_archive_user` بالاستبدال | خطر إسقاط فرع قائم — تُنسخ الدالة كاملةً وتُختبر كل الفروع القديمة قبل/بعد. |
| 12 | اختلاف السياسة بين الورديات | مفتاح `team` في `leave_policies` يفصلها؛ owner يضبط أي وردية، admin ورديته فقط. |
| 13 | أنصاف الأيام / إجازة ساعية | غير مدعومة الآن؛ `numeric(5,1)` يترك الباب مفتوحاً مستقبلاً. |

## 8) نقاط تحتاج قرارك قبل التنفيذ
1. عدّ الأيام: تقويمية أم أيام عمل؟ وهل تُستثنى العطل الرسمية؟
2. أي الأنواع «بلا حدّ» (عارض/غياب/مرافق مريض؟) وأي المستحقات السنوية الافتراضية لكل نوع محدود؟
3. الموظف الجديد: رصيد ابتدائي صريح أم تناسب آلي؟
4. عند تجاوز الرصيد: تنبيه فقط أم منع مع إلزام تجاوز المشرف؟
5. سقف الترحيل الافتراضي (`max_carryover`) لكل نوع.
